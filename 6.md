Exactly. This is the part I would design **before you start building the Payload collections**.

The key idea is: **don't store everything inside a "State" record.** Store entities separately and connect them with relationships. PostgreSQL then handles the relationships between them.

# 3. Pricing Rules

This is where your calculation engine becomes interesting.

Instead of storing:

```text
Arizona 3-ton 16-SEER2 = $7,502
Arizona 3-ton 18-SEER2 = $8,200
Arizona 4-ton 16-SEER2 = $9,000
...
```

you can store the **variables that produce the estimate**.

For example:

```text
Pricing Rule
────────────────────────
state: Arizona

labor_multiplier: 1.12
equipment_multiplier: 1.00
permit_base: 850

labor_rate: 315/hour
disposal_fee: 150
```

Then your application calculates:

```text
Base Equipment
        +
Adjusted Labor
        +
Permits
        +
Materials
        +
Other adjustments
        =
Estimated Cost
```

This is much easier to maintain.

# And here's how one page gets built

Let's say the visitor opens:

```text
/ac-cost-calculator/3-ton/16-seer2/arizona
```

Next.js extracts:

```text
state = arizona
tonnage = 3
seer2 = 16
```

Then:

### Step 1

Find State:

```text
Arizona
labor_index = 1.12
permit_cost = 850
climate = hot-dry
```

### Step 2

Find AC System:

```text
Central AC
3 ton
16 SEER2
equipment cost = $4,956
```

### Step 3

Find pricing rules:

```text
Arizona
labor multiplier = 1.12
permit = $850
```

### Step 4

Calculate:

```text
Equipment       $4,956
Labor           $2,530
Permits         $850
──────────────────────
Estimated       $7,502+
```

### Step 5

Retrieve Arizona-specific content:

```text
Arizona introduction
Arizona labor explanation
Arizona permit information
Arizona climate information
Arizona FAQs
Arizona sources
```

### Step 6

Render the page.

So the page isn't:

> "Take the same article and replace Idaho with Arizona."

Instead, it's:

> **Same application + different structured data + genuinely different local information.**

That's the architecture I'd recommend for your PSEO strategy.

## One change I'd make to your original collection list

I'd actually expand it slightly:

```text
Core
├── States
├── Cities              ← later
├── HVAC Systems
├── Pricing Rules
└── Pricing Data

Content
├── PSEO Pages
├── Content Blocks
├── FAQs
├── Blog Posts
├── Authors
└── Sources

Contractors
├── Contractors
├── Contractor Locations
├── Contractor Reviews
└── Contractor Services

Media
└── Media
```

**Don't build all of this on day one.**

Start with:

```text
States
HVAC Systems
Pricing Rules
PSEO Pages
FAQs
Sources
Blog Posts
Authors
```

Then add **Contractors** once the calculator/PSEO foundation is solid.

That keeps your Payload schema manageable while giving you a clean path from **HVAC cost calculator → local data platform → contractor discovery → affiliate monetization**.
