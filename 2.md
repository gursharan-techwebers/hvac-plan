Exactly. This is the part I would solve **before scaling the 1,400 pages**.

And there is an important distinction:

> **You do not need 1,400 completely different articles.**
>
> You need 1,400 pages where the **useful information changes appropriately for the specific query**, while common factual/UI components can remain shared.

Google does **not** require every page to have 100% unique text. The danger is publishing pages where the only meaningful difference is the URL, a number, and a few replaced words.

## The architecture I'd use

Instead of:

```text
Page
├── Same intro
├── Same calculator
├── Same 1,000-word article
├── Same FAQ
└── Replace:
      Texas → Florida
      3 Ton → 4 Ton
      $8,000 → $9,000
```

build pages from **content modules**.

```text
PSEO Page
│
├── Core calculator
│
├── Dynamic cost data
│
├── System-specific content
│
├── Efficiency-specific content
│
├── Location-specific content
│
├── Combination-specific insights
│
├── Cost factors
│
├── Methodology
│
├── Comparison
│
├── FAQs
│
└── Related resources
```

The important part is that **each module has a reason for existing**.

---

# 1. Separate your content into 4 levels

This is probably the most important architecture decision.

### Level 1 — Universal content

This can be shared.

For example:

> HVAC installation costs vary depending on equipment, labor, system size, efficiency, and installation complexity.

You don't need to rewrite this 1,400 times.

---

### Level 2 — System-specific content

Depends on the HVAC system.

For your current AC pages:

```text
system = central-ac
```

Later:

```text
system = heat-pump
system = furnace
system = mini-split
```

Central AC content can therefore be different from heat-pump content.

---

### Level 3 — Dimension-specific content

This is where your:

* tonnage
* SEER2
* state

come into play.

For example:

**3-ton**

could explain:

* typical application
* approximate home size range
* sizing considerations
* oversizing concerns

While:

**5-ton**

could explain:

* larger homes
* higher equipment cost
* installation considerations
* ductwork implications

Likewise, 14 SEER2 vs 16 vs 18 should have meaningful differences.

---

### Level 4 — Combination-specific content

This is the most valuable layer.

Instead of separately saying:

> 3 ton information

and:

> Texas information

you can generate an insight about their **combination**.

For example:

> A 3-ton system is commonly considered for smaller-to-medium residential applications, but actual sizing should be determined through a proper load calculation rather than square footage alone. In Texas, cooling demand can be substantial because of the state's hot climate, making correct sizing and efficiency particularly important.

That's genuinely relevant to:

**3 Ton + Texas**

rather than simply inserting "Texas" into a template.

---

# 2. Don't create 1,400 manually written pages

That would be insane to maintain.

Instead, build a **content data model**.

For example:

```ts
type StateContent = {
  name: string;
  climate: string;
  pricingFactors: string[];
  hvacConsiderations: string[];
  localFactors: string[];
};
```

Then:

```ts
const texas = {
  name: "Texas",
  climate: "...",
  pricingFactors: [...],
  hvacConsiderations: [...],
  localFactors: [...]
};
```

And separately:

```ts
type TonnageContent = {
  tonnage: number;
  typicalUse: string;
  sizingNotes: string[];
};
```

Then:

```ts
const threeTon = {
  tonnage: 3,
  typicalUse: "...",
  sizingNotes: [...]
};
```

And:

```ts
type SeerContent = {
  seer2: number;
  efficiencyDescription: string;
  costConsiderations: string;
};
```

Now the page engine combines these.

---

# 3. But don't just concatenate everything

This is where many PSEO systems go wrong.

You don't want:

```text
Texas paragraph
+
3-ton paragraph
+
16-SEER2 paragraph
+
generic paragraph
```

and call that unique content.

Instead, create **conditional content relationships**.

For example:

```text
IF state = Texas
AND tonnage >= 4
AND seer2 >= 18

→ show high-efficiency/larger-system insight
```

Or:

```text
IF state = Florida
AND system = central AC

→ emphasize cooling demand, humidity and installation considerations
```

That produces genuinely contextual information.

---

I'd create a structured dataset like:

Now the page contains **useful data**, not just text.

# 6. Add "What drives this estimate?"

This should dynamically explain the actual combination.

For:

**3 Ton / 16 SEER2 / Texas**

you might generate:

### What drives this estimate?

> The estimate reflects a 3-ton cooling system with a 16 SEER2 efficiency rating in Texas. System size affects equipment and installation costs, while the efficiency rating can increase equipment cost compared with lower-efficiency models. Regional labor and installation conditions also influence the final price.

For:

**5 Ton / 18 SEER2 / California**

the explanation should materially change.

That's much better than:

> "This 5-ton 18 SEER2 system in California costs..."

---

# 7. Give every page a meaningful "Why this number?"

This is something I'd make part of the product.

For example:

### Why does a 3-ton 16 SEER2 system cost this much?

Then explain the estimate using the actual variables.

This creates an excellent UX **and** gives you another meaningful content layer.

---

# 8. State content should be more than the state name

This is where I would spend significant effort.

Don't have:

> Texas HVAC costs can vary depending on location.

Instead, your state dataset should eventually contain:

```text
Texas
├── Climate
├── Cooling demand
├── Common HVAC systems
├── Labor considerations
├── Permit considerations
├── Energy considerations
├── Utility considerations
├── Rebates/incentives
├── Regulatory information
└── Sources
```

Then your Texas page actually deserves to exist.

And Florida deserves to exist separately.

---

# 9. Don't create fake differences

This is critical.

If you don't have meaningful data for a state, **don't manufacture it just to make the page unique**.

For example, don't have AI write:

> "Florida homeowners often prefer 16 SEER2 systems because Florida's unique HVAC market..."

unless you actually have evidence for that statement.

Better:

> "Actual installation costs vary by contractor, equipment, home conditions, and local labor rates."

Honest general information is better than fabricated specificity.

---

# 10. Use editorial content to fill the gaps

You don't need every single PSEO page to have massive text.

Suppose:

**3 Ton / 14 SEER2 / Texas**

and

**3 Ton / 16 SEER2 / Texas**

have very similar educational content.

That's okay.

The pages can still be valuable because the **calculator data and comparison are different**.

Then link both to a strong editorial guide:

> **14 vs 16 SEER2: What Is the Difference?**

That guide can explain the subject comprehensively once.

This is much better than generating 1,400 variations of the same explanation.

---

# 11. Build a content similarity test into your Next.js system

This is something I'd actually implement.

Before publishing pages, calculate similarity between generated content.

You can have your build/content pipeline flag pages that are too similar.

Conceptually:

```text
Generate page
      ↓
Extract content
      ↓
Compare against existing pages
      ↓
Similarity > threshold?
      │
   ┌──┴──┐
  YES    NO
   │      │
Flag    Publish
```

For example, you could flag pages where the **main informational content** is 85–90% identical.

But don't treat the threshold as a Google rule. It's simply an **internal quality-control mechanism**.

---

# 12. I'd also create a "page value score"

For your 1,400 URLs, have your system evaluate whether each page contains enough meaningful information.

For example:

```text
Calculator works                 +20
Unique cost data                 +20
State-specific data              +15
Tonnage-specific explanation     +10
SEER2-specific explanation       +10
Combination insight              +10
Relevant comparison              +5
Sources                          +5
Useful related resources         +5
------------------------------------
Maximum                          100
```

Then:

```text
90–100 → Excellent
75–89  → Good
60–74  → Review
<60    → Don't index yet
```

Again, **this isn't Google's scoring system**. It's your internal publishing standard.

This is exactly the sort of engineering approach I'd take with 1,400 pages.

For:

## The key mindset

Don't ask:

> **"How do I make 1,400 pages different?"**

Ask:

> **"What information does someone searching this exact combination need that they wouldn't get from another combination?"**

That's the difference between **PSEO content spinning** and a **real programmatic data product**.

And for HVAC Cost Buddy, I think the second approach is absolutely the one you should build.
